# MathModel-DE-Skill End-to-End Specification

> 最终目标：用户提供一份 CUMCM D/E 题题目及全部附件，Skill 能够完成从题意理解、数据处理、模型建立、计算求解、验证、可视化到论文写作的完整闭环，并输出可复现、可追溯、符合数学建模竞赛写作规范的最终成果。

## 1. 产品级成功标准

本 Skill 的最终验收单位不是单个模型、单个 Python 模板或单个分析报告，而是：

```text
题目 + 全部附件
        ↓
可执行建模项目
        ↓
各问题模型与计算结果
        ↓
验证与证据
        ↓
完整数学建模论文
```

一次端到端运行至少应能够产生：

1. 结构完整的数学建模论文材料；
2. 每个问题对应的模型与结果；
3. 与真实计算结果对应的图表；
4. 可复现代码与运行记录；
5. 模型选择、比较与验证证据；
6. 从论文结论反向追溯到模型、代码、运行记录和输入数据的证据链。

## 2. 输入契约

### 2.1 必需输入

- 竞赛题目文本，或可读取的题目文档；
- 题目要求使用的附件。

### 2.2 可选输入

- 用户指定的建模偏好；
- 用户指定的软件/语言；
- 用户已有代码；
- 用户已有分析结果；
- 用户指定的论文格式或模板。

### 2.3 输入原则

Skill 必须区分：

- 题目明确给出的事实；
- 附件中实际存在的数据；
- 根据题意形成的建模假设；
- 模型推断出的结果。

不得把推断结果伪装成题目事实或原始数据。

## 3. 端到端阶段

```text
00 Start
   ↓ ProblemSpec
01 Analysis
   ↓ ProblemMap
02 Data
   ↓ DataProfile
03 Modeling
   ↓ ModelPlan + ModelSpec
04 Compute
   ↓ RunManifest + ResultBundle
05 Visualization
   ↓ Figure / Table Evidence
06 Verification
   ↓ VerificationReport
07 Writing
   ↓ PaperEvidence + Paper
Final Submission Gate
   ↓
Final Package
```

每个阶段必须消费上游 Artifact，并产生可供下游继续工作的结构化结果。不得主要依靠不可追踪的自然语言上下文传递状态。

## 4. Stage 00 — Start

### 目标

把题目和附件转换成一个可执行的建模项目。

### 必须完成

- 识别 D/E 或其他任务特征；
- 读取并登记所有附件；
- 建立问题编号；
- 识别题目中的显式约束、目标和输出要求；
- 建立项目目录与任务清单。

### 输出

- ProblemSpec
- 项目计划
- todo
- 输入文件清单

### Gate

必须确认：题目已读取、问题编号完整、附件清单完整、关键约束未遗漏。

## 5. Stage 01 — Analysis

### 目标

回答“每一个问题究竟要解决什么”。

### 必须完成

对每一问明确：

- 任务类型；
- 输入；
- 输出；
- 决策变量/状态变量；
- 目标；
- 约束；
- 与其他问题的依赖关系；
- 候选方法族。

### 输出

ProblemMap。

### Gate

每一问必须有明确目标、输入、输出和约束；不得在问题尚未定义清楚时直接进入算法选择。

## 6. Stage 02 — Data

### 目标

把附件转换为可用于建模的、经过审计的数据资产。

### 必须完成

- 文件类型与规模检查；
- 表结构/schema检查；
- 单位与量纲检查；
- 缺失值、重复值、异常值检查；
- 时间、空间、实体关系检查；
- 数据质量报告；
- 必要的清洗、转换和特征构造；
- 记录每一步数据处理。

### 输出

DataProfile，以及必要的数据处理脚本/中间数据。

### Gate

数据来源、处理过程和可用字段必须清楚；禁止在没有证据的情况下填补关键数据或伪造参数。

## 7. Stage 03 — Modeling

### 目标

建立能够回答题目问题的数学模型，并证明选择该模型有理由。

### 标准路径

```text
任务类型识别
→ baseline
→ 候选模型
→ 模型比较
→ 最终模型
```

### 每个核心模型至少记录

- 建模目的；
- 适用条件；
- 建模假设；
- 变量及符号；
- 参数及来源；
- 目标函数/方程；
- 约束条件；
- 求解算法；
- 验证方法；
- 局限性。

### 模型升级原则

复杂模型只有在 baseline 存在明确不足时才升级，例如：

- 拟合/预测性能不足；
- 非线性或交互关系无法表达；
- 约束无法满足；
- 时空结构无法表达；
- 不确定性需要显式建模。

### 输出

- ModelPlan
- ModelSpec
- ModelComparison（适用时）

### Gate

模型选择必须有证据。存在合理候选模型时，应进行定量比较、交叉验证、敏感性分析或其他适当验证，而不是只给出主观选择。

## 8. Stage 04 — Compute

### 目标

把 ModelSpec 转换为真实、可复现的计算结果。

### 必须记录

- 输入数据引用；
- 数据处理版本；
- 模型版本；
- 代码路径/版本；
- 参数；
- 随机种子（随机算法适用时）；
- 软件环境；
- 运行时间；
- 输出文件；
- 运行状态。

### 输出

- RunManifest
- ResultBundle

### Gate

计算结果必须能够回答：

> 这个数字是用什么数据、什么模型、什么代码、什么参数、哪一次运行得到的？

## 9. Stage 05 — Visualization

### 目标

把真实计算结果转换为论文可用的图表和证据。

### 原则

- 图表只能来自真实数据或真实计算结果；
- 图表标题、单位、图例和编号完整；
- 图表中的核心数字必须可追溯；
- 不为了“好看”改变真实结果；
- 图表应服务于模型解释、结果比较和结论表达。

### 输出

- Figure/Table artifacts
- PaperEvidence 中的图表证据

## 10. Stage 06 — Verification

### 目标

回答“这些结果是否值得相信”。

### 验证层级

1. **数学正确性**：公式、推导、单位、边界；
2. **计算正确性**：代码运行、异常、数值稳定性；
3. **模型有效性**：拟合、预测、残差、误差、可行性；
4. **比较验证**：baseline/候选模型、交叉验证、留出集等；
5. **稳健性**：敏感性、扰动、参数变化；
6. **独立性验证**：必要时采用不同算法/实现/数据切分；
7. **可复现性**：同一输入和配置应能重新得到一致或可解释的结果。

“程序运行成功”不等于“模型验证通过”。

### 输出

VerificationReport。

## 11. Stage 07 — Writing

### 目标

将已验证的模型、结果和证据组织成数学建模论文。

### 论文内容至少覆盖

- 摘要；
- 关键词；
- 问题重述；
- 问题分析；
- 模型假设；
- 符号说明；
- 各问题模型建立与求解；
- 结果分析；
- 模型验证；
- 模型评价；
- 结论；
- 参考文献；
- 必要的附录/代码说明。

### 核心规则

论文不是独立创作层，而是证据的表达层。

禁止：

- 自行创造论文数字；
- 把未经验证的中间结果写成最终结论；
- 删除模型失败或限制而制造虚假的确定性；
- 将相关性写成因果关系。

## 12. Final Submission Gate

只有以下条件全部满足，才允许输出“最终论文”：

### A. 题目覆盖

所有题目问题均已处理，或明确记录无法完成的原因。

### B. 数值一致

论文、结果文件、图表和最终结论中的核心数字一致，或存在明确的舍入说明。

### C. 模型可追溯

每个核心结论均能追溯至对应 ModelSpec。

### D. 计算可追溯

每个核心数字均能追溯至 RunManifest、代码和输入数据。

### E. 图表可追溯

每个论文图表均能定位到真实数据/结果来源。

### F. 验证完成

核心模型具有与任务相适应的验证证据。

### G. 论文完整

论文结构完整，数学表达、变量、单位、编号和引用关系基本规范。

### H. 无虚构

不存在无法追溯的核心数据、参数、结果或引用。

## 13. 最终输出包

建议标准化为：

```text
final_output/
├── paper/
│   ├── paper.docx
│   ├── paper.pdf
│   └── evidence_index.md
├── results/
│   ├── problem_1.*
│   ├── problem_2.*
│   └── ...
├── figures/
├── tables/
├── code/
├── verification/
│   └── VerificationReport.md
└── manifest/
    └── final_manifest.json
```

其中 `evidence_index.md` 或等价文件应能帮助检查者从论文结论反查 Artifact、运行和数据。

## 14. 失败处理

端到端 Skill 不要求所有题目都“强行完成”。当某一环节失败时，应：

```text
发现问题
→ 定位 Stage
→ 保存失败 Artifact / 日志
→ 尝试替代方案
→ 重新验证
→ 若仍失败，明确报告失败原因
```

禁止为了通过 Final Gate 而伪造结果、跳过验证或删除失败证据。

## 15. D/E 泛化要求

该规格不绑定某一道历史题。

D/E 的具体模型、算法和知识只作为候选空间与先验。任何新增能力都必须证明其可以服务于一类问题，而不是只服务于某一道历史题。

## 16. 端到端验收测试

仓库最终应建立至少一组端到端 benchmark：

```text
输入题目 + 附件
→ 生成全部核心 Artifact
→ 通过各阶段 Gate
→ 得到真实计算结果
→ 生成图表证据
→ 通过 Verification Gate
→ 生成论文材料
→ 通过 Final Submission Gate
```

验收指标不只包括“代码是否运行”，还应包括：

- 问题覆盖率；
- Artifact 完整率；
- 结果追溯覆盖率；
- 模型选择证据覆盖率；
- 验证覆盖率；
- 论文数字一致性；
- 图表证据覆盖率；
- 端到端可复现性。

## 17. 最终产品原则

> **不是让 AI 看起来“会做数学建模”，而是让 AI 真正完成一次可检查、可复现、可追溯的数学建模生产流程。**

最终评价标准是：

> **给题目和附件，能否稳定地产出一篇有模型、有计算、有验证、有图表、有结论，而且每个关键结果都能追溯到数据、模型和代码的数学建模论文。**
