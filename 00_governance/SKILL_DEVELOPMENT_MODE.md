# Skill Development Mode：项目总目标与工作边界

## 1. 项目真正目标

`MathModel-DE-Skill` 的交付物是**一套面向 CUMCM D/E 题的可复用数学建模 Skill**，不是某一道历史题的答案。

历史题、题目 PDF、Excel、路网图等附件，首先是：

1. **能力需求来源**：告诉我们 Skill 还缺什么；
2. **benchmark**：测试 Skill 能否正确识别、分析、建模、验证；
3. **regression test**：防止以后修改 Skill 后已有能力退化；
4. **案例素材**：帮助抽象通用方法。

只有用户明确要求“解这道题”“继续做这道题”“给出最终答案”时，才切换到单题 Problem Solving 模式。

## 2. 三种工作模式

### A. Skill Development（默认）

```text
题目/附件
→ 能力缺口
→ 通用抽象
→ Skill 规则
→ Python 模板/模块
→ benchmark
→ 测试
→ 文档
→ GitHub 提交
```

完成标准是**仓库能力增强**，不是历史题最终答案。

### B. Benchmark / Regression Test

用真实历史题检验：

- 题型识别；
- 数据体检；
- 模型选择；
- 求解模板；
- 验证门禁；
- 图表规范；
- 论文流水线。

允许运行真实历史数据，但结果主要用于测试 Skill 的执行链路和正确性，不把题目变成一次性项目。

### C. Problem Solving

只有用户明确要求时进入。此时才以该题的最终建模结果、数值结果和论文答案为目标。

## 3. 当前 2024E 的正确定位

2024E《交通流量管控》不是当前项目的“待完成作业”，而是当前 Skill 的一个**高价值 E 题 benchmark**。

从它已经暴露出的能力需求中，应优先沉淀通用模块：

| 题目暴露能力 | 应沉淀为 Skill 能力 |
|---|---|
| 100 万级车辆事件数据 | 大文件分块读取、数据体检、摘要生成 |
| 车辆ID+时间+节点 | 事件流排序与轨迹重构 |
| 节点/路段/距离 | 图网络建模与拓扑校验 |
| 四方向编码 | 类别字典与方向标准化 |
| 时段划分 | 时序聚合、变点检测、聚类 |
| 左/直/右转不可直接观测 | 隐变量/轨迹推断框架 |
| 信号灯配置 | 约束优化、交通流目标函数 |
| 停车巡游识别 | 轨迹特征、规则 baseline、分类模型 |
| 管控效果评价 | 干预前后比较、时空对照、稳健性分析 |
| 题目附件多源融合 | schema、实体对齐、跨附件一致性检查 |

## 4. 典型错误：不要这样做

收到 2024E 题目和附件后，不应默认执行：

```text
读取附件2
→ 直接计算 Q1
→ 得到 Q1 答案
→ 继续 Q2/Q3/Q4
```

如果当前任务是完善 Skill，这样做会把大量一次性工作误认为 Skill 能力建设。

正确做法是：

```text
读取 2024E
→ 识别“百万级事件流 + 轨迹 + 路网 + 时序 + 优化 + 干预评价”
→ 判断仓库已有能力
→ 找到缺口
→ 增加通用模块/模板/规则
→ 将 2024E 纳入 benchmark
→ 测试模块
→ 记录结果
```

## 5. 通用化要求

任何由历史题产生的新代码都必须回答：

- 能否通过配置文件替换题目字段？
- 能否用于另一道 D/E 题？
- 是否把业务规则和算法逻辑分离？
- 是否有输入 schema？
- 是否有输出 schema？
- 是否能写 smoke test？
- 是否能记录 run manifest？
- 是否能验证结果而不是只运行程序？

如果答案是否定的，应继续抽象，而不是把一次性脚本直接放进通用模板。

## 6. 当前优先级

2024E benchmark 暴露的优先能力建设顺序：

1. 大文件数据审计与摘要；
2. 通用事件流/轨迹重构；
3. 网络拓扑与节点事件融合；
4. 时序聚合与时段识别；
5. 隐变量转向推断的通用框架；
6. 交通/网络类约束优化模板；
7. 干预前后效果评价模板；
8. benchmark regression tests；
9. 再用 2024E 做端到端回归测试。
