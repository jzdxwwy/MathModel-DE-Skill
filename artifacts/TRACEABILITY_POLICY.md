# Artifact Traceability Policy

## 1. Core principle

**Every material result must be traceable.**

A numerical conclusion, table, figure, model parameter, optimization decision, or paper claim must be traceable through a reproducible chain to:

```text
Problem / Task
    ↓
Input Data
    ↓
Data Processing
    ↓
Model Selection
    ↓
Model Specification
    ↓
Code / Algorithm
    ↓
Run Manifest
    ↓
Result Bundle
    ↓
Verification Evidence
    ↓
Paper Evidence / Claim
```

If a result cannot be traced through this chain, it is not eligible for a final conclusion without an explicit limitation statement.

## 2. Model-selection evidence

Choosing a model or algorithm is itself a modeling conclusion and must have evidence.

The Skill should record, when applicable:

- why the candidate model fits the problem structure;
- what assumptions make the model applicable;
- what data are required and whether those data are available;
- what constraints the model satisfies;
- why alternatives were rejected or ranked lower;
- what metric or validation evidence supports the selection;
- interpretability, computational cost, robustness, and reproducibility considerations.

Do not select a model merely because it is more advanced.

## 3. Comparison and cross-validation

Comparison is required when model choice is materially uncertain, when multiple plausible algorithms exist, or when a stronger claim needs independent evidence.

Preferred comparison levels, from lower to higher evidence strength:

1. baseline comparison;
2. candidate-model comparison under the same data split and metric basis;
3. holdout or cross-validation;
4. sensitivity / robustness analysis;
5. independent implementation or alternative algorithm cross-check;
6. repeated or resampled validation when statistically appropriate.

Not every problem requires every level. The Skill should choose the minimum sufficient validation burden and explain why.

## 4. No false independence

Two implementations that share the same flawed assumption, preprocessing error, leakage, or input data issue are not independent validation merely because different code was used.

Cross-validation and cross-checking must be evaluated for genuine independence of evidence.

## 5. Provenance requirements

Every executable result should retain, where available:

- input artifact references;
- preprocessing references;
- model specification reference;
- algorithm / code reference;
- run identifier;
- environment or dependency information;
- random seed when stochastic;
- output artifact references;
- verification report reference.

Hashes or immutable version identifiers should be used when the environment supports them.

## 6. Reproducibility requirements

A result is reproducible only when another run can reconstruct the relevant inputs, model, code, configuration, and randomness controls.

"The program was run" is not sufficient provenance.

## 7. Writing rule

Paper claims must point to evidence rather than to prose generated by the model.

For example:

```text
Claim C-03
  ↓
ResultBundle R-17
  ↓
RunManifest RUN-17
  ↓
ModelSpec M-04
  ↓
Code commit / file
  ↓
DataProfile D-02
```

Figures and tables used as evidence should themselves reference the result that generated them.

## 8. Gate rule

A stage may pass only when its required upstream artifacts are present, valid, and traceable.

The final gate should reject:

- unsupported numerical claims;
- unexplained model choices;
- results with missing input/code provenance;
- figures whose source results cannot be identified;
- validation claims without recorded evidence;
- comparisons performed on inconsistent data or metrics without disclosure.

## 9. Practical principle

The Skill should prefer:

> **one clear, reproducible, well-validated model over a collection of impressive but untraceable models.**
